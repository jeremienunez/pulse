# Contributing

This repo packages one plugin, `pulse`, with its package surface rooted at the repository top level. Use this guide when creating or editing skills, updating manifests, or changing the public workflow contract.

Start with the [documentation index](docs/README.md), [architecture](docs/ARCHITECTURE.md) and [workflow guide](docs/workflow.md). The distribution branch is `tuned/main`; plugin and marketplace identifiers remain `pulse` and `pulse-dev`.

## Repository Truth

These paths matter most:

- [`workflow/`](workflow) is the source of truth for the seven core routing/stage skills; [`skills/`](skills) remains canonical for support skills and generated package output
- [`.codex-plugin/plugin.json`](.codex-plugin/plugin.json) is the Codex package manifest
- [`.claude-plugin/plugin.json`](.claude-plugin/plugin.json) is the Claude plugin manifest
- [`.mcp.json`](.mcp.json) is the packaged MCP manifest for shared runtime servers
- [`scripts/build-antigravity-dist.mjs`](scripts/build-antigravity-dist.mjs) derives the native Antigravity manifest and MCP configuration from the common package
- [`.agents/plugins/marketplace.json`](.agents/plugins/marketplace.json) exposes the packaged `pulse` plugin to Codex
- [`scripts/sync-skills.sh`](scripts/sync-skills.sh) mirrors the canonical skills tree into raw skill directories for other runtimes
- [`AGENTS.md`](AGENTS.md), [`README.md`](README.md), and this file are public contract docs and must stay in sync with the actual skills

## Plugin Packaging Overview

This repository is structured as a root-scoped packaged plugin repo. It ships a single plugin, `pulse`, from the repository root.

- The Codex package manifest lives at [`.codex-plugin/plugin.json`](.codex-plugin/plugin.json). The current release packages skills and MCP servers but no lifecycle hooks.
- Onboarding is explicit and optional for v2. It may install helpers under `.pulse/scripts/`, but must not create legacy state mirrors for an active v2 run.
- The Claude manifest lives at [`.claude-plugin/plugin.json`](.claude-plugin/plugin.json). It declares the packaged skill directory and shared MCP config for Claude Code.
- Claude metadata remains version-aligned and buildable, but Codex is the blocking release target.
- The repo-level marketplace at [`.agents/plugins/marketplace.json`](.agents/plugins/marketplace.json) exposes the packaged `pulse` plugin to Codex. When Codex opens a clone of this repo, it reads the marketplace file and offers `pulse` for installation.
- Skill discovery is automatic. Run `node scripts/build-workflow-skills.mjs` before catalog generation whenever a canonical core contract changes.
- Antigravity CLI consumes the native distribution generated by `scripts/build-antigravity-dist.mjs`; its payload retains the common workflow and helpers. Verify the staged and installed payload with `agy plugin validate --strict --json` and the installed manifest hashes.
- The standalone `cli-bridge` skill is distributed with `scripts/install-cli-bridge.mjs`, which preserves foreign skill directories and carries its own helper. Other raw mirrors remain available through [`scripts/sync-skills.sh`](scripts/sync-skills.sh).

## SKILL.md Format

Every skill needs a `SKILL.md` with YAML frontmatter and a markdown body.

```yaml
---
name: my-skill
description: >-
  Use when this skill clearly applies. State the trigger scenarios, the kinds
  of requests it handles, and the artifacts or outcomes it produces.
metadata:
  version: '1.0'
  ecosystem: pulse
---

# My Skill

Operational instructions the agent follows when the skill is invoked.
```

### Required Fields

| Field | Purpose |
|-------|---------|
| `name` | Bare public skill identifier in frontmatter. Use hyphen-case that matches the directory; the plugin/runtime adds `pulse:` for ecosystem skills |
| `description` | Trigger text for skill matching. This is the most important field |

### Common Optional Fields

| Field | Example | Purpose |
|-------|---------|---------|
| `metadata.version` | `'1.1'` | Track revisions |
| `metadata.ecosystem` | `pulse` | Group related skills |
| `metadata.type` | `bootstrap`, `support`, `meta` | Classify the role |
| `metadata.position` | `'4 of 9'` | Document chain placement when useful |
| `allowed-tools` | `Read, Write, Bash` | Restrict tools |
| `model` | `claude-sonnet-4-20250514` | Request a model |
| `mode` | `ultrathink` | Thinking mode preference |
| `license` | `MIT` | License declaration |

## Writing Good Descriptions

Descriptions decide whether a skill fires. Treat them as search metadata, not as mini-instructions.

Good:

```yaml
description: >-
  Systematic debugging for blocked work, test failures, build errors, runtime
  crashes, and integration issues in Pulse. Use when a worker is stuck, a
  verification step fails, or reviewing/UAT hands the work back.
```

Bad:

```yaml
description: Helps with debugging things
```

A strong description:

- starts with clear trigger scenarios
- includes user verbs such as `build`, `plan`, `review`, `debug`, `simplify`
- mentions outputs when that sharpens routing, such as `writes CONTEXT.md` or `creates review beads`
- stays concise enough to be scanned as metadata
- avoids retelling the workflow, because agents can mistake description text for the full instructions

## Skill Directory Layout

Use this shape by default:

```text
my-skill/
├── SKILL.md
├── references/
├── scripts/
└── agents/
```

Conventions:

- `SKILL.md` is required
- `references/` holds templates, probes, rubrics, and reference notes that the skill explicitly tells the agent to read
- `scripts/` holds executable helpers the skill invokes; add `__pycache__/` to `.gitignore` if scripts are Python
- `agents/` holds subagent configuration or prompt files (e.g., OpenAI-compatible YAML configs)
- shared packaged MCP servers should be declared at [`.mcp.json`](.mcp.json); avoid per-skill MCP manifests unless a skill genuinely owns a private runtime contract
- avoid adding extra human-only files inside skill directories unless they are genuinely part of the runtime contract; contributor-facing docs should live at repo root or under `references/`

`references/` files are never auto-loaded. The `SKILL.md` body must explicitly tell the agent when to read them.

## Pulse Workflow Conventions

Skills in the `pulse:` namespace inherit extra rules.

### Bootstrap and Chain Order

Pulse sessions start with the router/scout:

```text
pulse:using-pulse
```

`pulse:preflight` is a separate diagnostic invoked only when the user explicitly requests a readiness/onboarding check.

The delivery chain is:

```text
pulse:exploring -> pulse:planning -> pulse:validating -> pulse:executing -> pulse:reviewing -> pulse:compounding
```

`pulse:swarming` is an approved execution strategy inside Stage 04, not a chain stage.

Support routing may also invoke `pulse:systematic-debug-fix`, `pulse:worktree-isolation`, `pulse:governed-feature`, or `pulse:dream`. `governed-feature` remains an overlay owned by the Pulse lifecycle, while `worktree-isolation` protects user state and establishes a clean implementation baseline.

`pulse:design` owns design/cultural/motion methods; `pulse:visual-assets` owns capability selection and the brand-family recipe. Keep each entry below 600 words and first-level guide below 1,000. Share one cultural method and task research, and preserve conditional activation. A catalogue record does not prove a local engine/export. Keep native SVG grammars separate and external runtime/private catalogues outside the package. Update [provenance](docs/design/design-expression-provenance.md) and the [evaluation record](docs/evaluation/design-expression-assets.md), preserving frozen scenarios, omissions, unknown metadata and passing regression constraints. New native creative sessions use approved1.1 inputs; historical1.0 evidence is read without migration.

### Hard Contract Rules

- Never execute without `pulse:validating`
- `history/<feature>/run.json` plus numbered stage outputs are the v2 source of truth
- `small_change` mode still validates and reviews; it only reduces depth
- `P1` review findings always block merge
- v2 pause/resume uses a stage-local handoff referenced by `run.json.resume_path`; legacy keeps owner-scoped handoffs
- v2 chain skills must not write legacy state mirrors

### Work Graph Contract

Planning and validating write one immutable `work-graph.json`. Every node must declare:

- `id`
- `title`
- `depends_on`
- `files`
- `verification`

Execution state is a separate Stage 04 artifact. Beads may project the approved graph only when Gate 3 selects swarm.

- `change` and `preserve` beads include `behavior_steps` with honest `baseline`, `retest`, and relevant `regression` evidence.
- `investigate` beads include `investigation_steps` for reproduction and root-cause tracing before any production intervention is authorized.
- Use the lowest sufficient verification layer and preserve the repository's existing test stack. Gherkin, Cucumber, browser automation, and test-first ceremony are not required.
- If implementation predates a scenario, compare it against the pre-change baseline, a controlled reverse application, or equivalent evidence; do not discard valid code for ordering ceremony.

### Reviewing and Debugging

Public docs and skill changes should preserve these current behaviors:

- `pulse:reviewing` is root-owned by default, with specialist agents only on explicit operator request; artifact verification, review intake and human UAT remain part of review
- verification evidence is a first-class artifact, not a vague claim in prose
- `pulse:systematic-debug-fix` keeps blocked or failing work root-cause-first and adds regression lock-down before the work is considered done

## Adding a New Skill

1. For a core chain stage, edit its canonical contract under `workflow/stages/` and regenerate skills. For a support skill, create the directory under [`skills/`](skills):

   ```bash
   mkdir -p skills/my-skill
   ```

2. Write `SKILL.md` only for support skills; core `SKILL.md` files are generated.

3. Add `references/`, `scripts/`, or `agents/` only when the skill really needs them.

4. Codex discovers packaged skills from the plugin root `skills/` directory, so no per-skill manifest change is needed.

5. If you need raw skill mirrors for another runtime, verify `bash scripts/sync-skills.sh --dry-run` still links the skill from the canonical tree.

6. Update any public docs that mention the changed contract. That often includes:
   - [`README.md`](README.md)
   - [`CONTRIBUTING.md`](CONTRIBUTING.md)
   - [`AGENTS.md`](AGENTS.md)
   - lineage docs under [`references/lineage/`](references/lineage)

7. Test the skill end to end.

## Testing a Skill

Minimum check:

1. Build or install the exact candidate you changed. Follow the [installation guide](docs/installation.md) for runtime-specific commands and verify the installed payload. A remote marketplace install can still point to published bytes rather than local edits:
   - **Codex:** the catalog at [`.agents/plugins/marketplace.json`](.agents/plugins/marketplace.json) identifies `pulse@pulse-dev` and pins its source to `tuned/main`.
   - **Claude Code:** register the intended local checkout and install the whole `pulse@pulse-dev` plugin, then verify the resulting cache against the candidate.
2. Start a fresh session
3. Ask for something that should trigger the skill
4. Verify the right skill is discovered and the body instructions are followed

For Pulse ecosystem skills, use [`pulse:writing-pulse-skills`](skills/writing-pulse-skills/SKILL.md). That skill is the repo-standard process for pressure testing:

- freeze pressure scenarios and scoring before observing outcomes
- run `BASELINE` without the candidate skill and record exact choices and rationalizations
- apply an `INTERVENTION` only when the baseline exposes a guidance-attributable gap
- run `RETEST` on the same frozen cases and record regressions as well as improvements
- when the baseline already passes, record that result and make no intervention

When editing chain skills, also test the surrounding contract:

- `preflight` remains explicit-request-only and `using-pulse` still routes correctly without it
- Gate 3 still blocks both execution strategies
- v2 gate hashes become stale after artifact edits
- legacy owner-scoped handoffs still resume without migration
- `node .pulse/scripts/pulse_status.mjs --json` still renders a valid read-only status snapshot after onboarding changes
- graph and execution-state schemas still line up across planning, validating, executing, and reviewing

## Documentation Rules

- use repository-relative links for files that live in this repo
- external links are fine when you are citing upstream projects or public documentation
- never commit absolute local filesystem paths such as `/Users/...`
- verify links point to real files
- treat drift between docs and shipped skills as a bug

This repo treats these as errors:
- a Markdown link uses an absolute local path
- a repository-relative Markdown link points to a missing target

Run:

```bash
bash scripts/check-markdown-links.sh
```

For repo-level verification, also run:

```bash
bash scripts/sync-skills.sh --dry-run
node scripts/build-workflow-skills.mjs --check
node scripts/build-skill-catalog.mjs --check
```

The Markdown link checker covers a selected set of entry docs and examples. When editing other guides, also check their relative links and heading anchors. Keep the [documentation index](docs/README.md) current when adding a public guide.

For the source quality gate, use the shared profiles described in [Git quality checks](docs/git-quality-hooks.md):

```bash
node scripts/pulse-quality.mjs --profile commit
node scripts/pulse-quality.mjs --profile ci --json
```

These commands inspect the Git index, not unstaged working files. Stage the intended candidate first. Prepare the declared external toolchain as documented in [code quality](docs/code-quality.md); checks do not install missing tools. Receipts establish the checks performed on that tree, not live CLI or model acceptance.

### Scout-First Startup

On onboarded repos, skills should prefer `node .pulse/scripts/pulse_status.mjs --json` as the first quick orientation step before opening deeper state files. The scout aggregates onboarding, tooling status, state mirror, handoff manifest, and learnings presence into a single read-only JSON snapshot that lets agents decide what to read next without opening every file individually.

## Standalone Skills

Standalone skills use the same `SKILL.md` structure, but they do not need Pulse chain handoffs or `.pulse/STATE.md` updates unless they explicitly integrate with the main workflow.
